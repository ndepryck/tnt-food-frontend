# 02 — Catalogue and live filters

Type a word from a recipe description into “Rechercher une recette”. The field changes immediately; after a 250 ms pause, the catalogue asks the server for matching cards. Now select an ingredient with “+ Ingrédient”. The dialog closes, a removable chip appears, and the cards must match **both** the text and the ingredient. A second chip reveals “Tous” and “Au moins un”: switching between them changes how the ingredients match, not how the text matches.

## Read the application diff in this order

1. [`Catalogue.tsx` — `Catalogue`](../../src/modules/recipes/Catalogue.tsx) owns the controls. Its **state** is the data React remembers between screen updates: the draft text drives the input, while the applied text, selected ingredients, match mode and sort drive the request. Only typing waits for the timer; “Effacer la recherche” clears both text values immediately, keeps the chips and focuses the text field.
2. [`catalogueQuery.ts` — `catalogueQuery`](../../src/modules/recipes/catalogueQuery.ts) translates those controls into an API payload. Text means `name CONTAINS text OR description CONTAINS text`; chips mean exact ingredient-name matches. The two groups are joined with `AND`. `remember` and `restore` save controls in `sessionStorage`, not recipe rows: returning in the same tab restores the inputs and requests fresh results.
3. [`usePagedSearch`](../../src/core/search/usePagedSearch.ts) owns the returned rows, loading status and next or failed offset. This **hook** (reusable React logic) starts each changed query at offset zero. [`searchRecipes`](../../src/modules/recipes/api/recipes.ts) and [`searchIngredients`](../../src/modules/recipes/api/ingredients.ts) specify their own filter and sort fields using the [shared search contract](../../src/core/search/contract.ts). Both use [`searchEndpoint`](../../src/core/search/searchEndpoint.ts) to POST the query and offset with a cancellation signal. Old requests are cancelled and late replies ignored. Existing cards stay readable until the new first page replaces them; “Plus de recettes” appends using the server’s `nextOffset`, and “Réessayer” repeats the failed offset.
4. [`IngredientPicker.tsx` — `IngredientPicker`](../../src/modules/recipes/IngredientPicker.tsx) owns a separate suggestion search, ten ingredients per page versus twelve recipes. Its **props** (inputs passed by `Catalogue`) include the selected ingredients to exclude and a function to call when the user chooses one. Type in “Rechercher un ingrédient”: the heading and input stay in place while the [results area](../../src/modules/recipes/catalogue.css) updates below them. Previous suggestions stay visible but their buttons are disabled until results for the new text arrive. Opening the dialog focuses its input; closing it or removing a chip focuses “+ Ingrédient”.
5. [`PageAction.tsx` — `PageAction`](../../src/modules/recipes/PageAction.tsx) shares keyboard behavior between the two lists without owning their data. If focus stays on the load/retry button, a successful append focuses the first new link or suggestion. If the user tabs away during loading, it leaves focus alone.

## Scenarios and check status

- [Component scenarios](../../tests/unit/modules/recipes/Catalogue.test.tsx): given a pending search, when typing settles, then only the current reply can replace the cards. The pagination scenarios cover retry at the failed offset and focus after the user tabs away. These tests control API replies rather than relying on server timing.
- [Browser scenario](../../tests/e2e/catalogue.spec.ts): given recipes with overlapping ingredients, when the user combines filters, reverses the sort and returns from a card, then matching cards and controls are restored. The recipe setup via API and ingredient setup via [fixture SQL](../../tests/e2e/fixtureSql.ts) belong to the test, not to the catalogue.
- [Delayed picker scenario](../../tests/e2e/catalogue.spec.ts#L6-L39): given a loaded ingredient, when the user types a term with no matches, then the previous option stays visible but disabled while the search is pending. The test holds the request before forwarding it to the real backend. It checks the dialog, heading and input bounds both while waiting and after the empty result arrives.
- **Verified after the picker fix (implementer):** all 13 unit tests, three real-backend browser checks and type checking passed. Earlier checks also covered the production build, fixture cleanup and catalogue widths from 320 to 1536 px.

## Try it yourself (suggested, not a completed check)

With recipes that share some but not all ingredients, select two chips, switch from “Tous” to “Au moins un”, choose “Nom Z–A”, open a card and return via “Recettes”. Expect the same chips and mode, with recipes containing either ingredient sorted by descending name. Only controls persist in the tab, not the number of pages loaded. This block supports browsing; “+ Nouvelle recette” is disabled.
